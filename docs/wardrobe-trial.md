# 衣橱试搭与首次推荐联调

## 配置与入口

复制 `.env.example` 为 `.env.local`，将 `EXPO_PUBLIC_WEATHER_API_URL` 设为后端根地址（不带 `/v1`）。后端必须包含多套推荐与反馈排序补丁。更改环境变量后完整重新加载 Expo 应用。真机访问本地后端时使用手机可访问的局域网地址。

首页「今日全天智能穿搭计划」选中时段 →「智能穿搭」→ 填写参考场合（默认「通勤」）→「用我的衣橱试搭」。所选时段预报不足时禁止发起请求，不用当前天气补齐。

首次进入会读取本机试搭记录；已有记录时展示原城市、时段、体感温度、场合及反馈。提交与重试始终使用这份快照。「开始新的试搭」会清除当前记录，下一次试搭采用最新衣橱及进入结果页时选择的天气。

## 当前请求契约

项目此前没有推荐接口客户端，也未提供后端仓库或完整 OpenAPI 定义。以下字段格式沿用当前前端模型，需与补丁后端核对：

- `weather`：使用 Open-Meteo 字段名，如 `apparent_temperature`、`temperature_2m`、`precipitation`、`weather_code`、`wind_speed_10m`，所选时段附带降水概率与温度范围。
- `wardrobe`：本机 `WardrobeItem[]`，含 `id/name/category/color/imageUri/createdAt`；类别为现有中文类别；不上传照片文件。
- `occasion`：用户输入的非空字符串，默认 `通勤`，反馈使用同一字符串。
- `items`：`top/outerwear/bottoms/shoes` 对应单品 ID 字符串或 `null`；`missingSlots` 是这些槽位名的数组。响应的完整 `items` 会直接保留到反馈中。

请求均为 `POST /v1/outfits/recommend`，`limit: 4`。首次不带反馈；正式推荐仅在有选择时附加：

```json
{
  "feedback": [{
    "items": {"top": "top-a", "outerwear": "outer-a", "bottoms": "pants-a", "shoes": "shoes-a"},
    "feelsLikeC": 16,
    "occasion": "通勤",
    "aesthetic": "like",
    "thermal": "tooCold"
  }]
}
```

客户端不筛掉不喜欢的上衣、不重新排序，也不虚构备选；正式响应第一套为首选，其他搭配按返回顺序循环。请求超时为 20 秒。读取、试搭、提交和本地保存失败均显示对应的重试入口。

## 自动验证

```sh
node --test tests/*.test.cjs
npx expo lint
npx tsc --noEmit
```

`tests/outfitTrial.test.cjs` 使用体感 16°C、通勤、多件中厚衣物 fixture，覆盖整套反馈、组合反馈及取消、快照不变、跳过、缺件、空组合、单套响应、网络失败重试、保存竞争与失败恢复、重启读取和照片 URI 映射。网络与 AsyncStorage 使用 mock；图片组件使用轻量原生组件替身渲染，因此这些测试不证明真机照片已成功解码或后端排序算法生效。

## 补丁后端部署后验收

1. 使用体感 16°C 的通勤天气和含多件中厚上衣、外套、裤子、鞋子的衣橱；在设备上核对每套真实照片、场合和体感，备选包含不同上衣或外套。
2. 首套选「不喜欢」并提交，检查请求包含四个槽位；确认合适备选能保留同一上衣、更换其他单品。客户端不会对单件作排除处理。
3. 新试搭选「喜欢＋预计太冷」，检查两项同条发送，对比实际返回排名；有更暖合适备选时应由后端调整排序。
4. 检查全部跳过时请求无 `feedback`；分别验证缺下装、正常不穿外套、全空、单套结果（无「换一套」）。
5. 断网提交后恢复网络重试，核对选择与三份上下文不变；退出并重新启动应用后进入结果页，确认反馈和原上下文恢复。
6. 本机衣橱为空时只显示上传引导；本地记录保存失败时保留本页选择并允许重试。

当前不附带测试衣物到真实衣橱，不改动后端，也不将 mock 排名结果当作实际联调结论。
